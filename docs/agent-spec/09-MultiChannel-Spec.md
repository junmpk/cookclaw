# 09. Multi-Channel Specification

## 1. 当前通道关系（AS-IS）

~~~mermaid
flowchart TD
    WEB[Web /api/v1/chat] --> CS[chat_stream]
    QQ[QQ Bot] --> QC[qqbot_chat]
    WA[WhatsApp Node Service] --> QC
    WX[微信 Microservice] --> QC
    CS --> CORE[意图/编排/搜索/QA]
    QC --> CORE
    CORE --> R[结构化结果]
    R --> WR[Web Markdown]
    R --> QR[QQ Markdown]
    R --> WAR[WhatsApp 文本 + 媒体卡片]
    R --> WXR[微信上传图片 + 文本卡片]
~~~

四通道入口固定进入同一 `_run_turn_orchestrator()` 与 `execute_turn()` 组合根，核心返回
`ResponseEnvelope`；三个 IM 使用 `IMResponseRenderer`，Web 使用 `WebResponseRenderer`
后再由 API 包装成原 SSE。运行时不再存在按通道切换的第二条文本主链。

## 2. 能力对比

| 能力 | Web | QQ | WhatsApp | 微信 |
|---|---|---|---|---|
| 文本问答 | 支持 | 支持 | 支持 | 支持 |
| 菜谱搜索 | 支持 | 支持 | 支持 | 支持 |
| 搜索等待提示 | 无统一 IM 式提示 | 支持 | 当前不一致 | 当前不一致 |
| 菜谱图片 | Markdown/URL | Markdown 图片 | 原生媒体消息 | 下载后上传原生媒体 |
| 食材展示 | 支持 | 当前卡片常省略 | 支持 | 按 adapter 展示 |
| 图片识别 | API 能力需单独入口 | 支持通道图片 | 支持 | 支持 |
| 候选连续追问 | 每个请求有独立 `web:` thread；跨 worker 待确认 | 支持 | 支持 | 支持 |
| 设备执行 | 复用确定性设备链 | 支持确定性设备链路 | 支持同一业务链 | 支持同一业务链 |

## 3. 当前一致性问题

1. Web 已签发独立 `web:` thread，但客户端必须复用响应头；匿名会话的 Redis 多 worker
   一致性和防冒用策略尚未在测试服务器验证。
2. 搜索等待提示和 token 级流式输出仍未形成统一协议。
3. 同一搜索结果在 Web、QQ、WhatsApp 展示的字段不同。
4. 图片错误、设备异常等兜底文案可能固定为中文，即使用户用英文。
5. WhatsApp/微信媒体发送拆成多条，部分成功时缺少统一的完成状态。
6. 图片派生事实和候选已进入统一状态/账本，但与文本搜索的长期画像口径仍不完全相同。

## 4. 安全与认证

审计发现以下边界需作为 P0：

- FastAPI WhatsApp webhook 当前未强制校验 Node 侧发送的 webhook secret；
- 微信 webhook 缺少等价签名/共享密钥校验；
- WhatsApp/微信登录、二维码、启动和状态等管理接口需要访问控制；
- Web chat 无用户鉴权；虽然默认会签发随机独立 thread，但登录账号映射、thread 防冒用和
  多 worker 会话一致性仍需生产方案；
- 通道身份不能直接等同于设备授权，必须额外绑定。

所有 webhook MUST 验证来源、时间戳/重放条件和密钥。管理接口 MUST 与普通消息回调分离，并限制网络和账号权限。

## 5. 目标统一响应模型（TO-BE）

业务层 SHOULD 返回通道无关结构：

~~~json
{
  "locale": "zh-CN",
  "intent": "recipe_search",
  "messages": [
    {"type": "text", "role": "lead", "text": "..."},
    {"type": "recipe_cards", "items": []},
    {"type": "text", "role": "next_step", "text": "..."}
  ],
  "context": {"candidate_set_id": "..."},
  "trace_id": "..."
}
~~~

Adapter 只根据通道能力渲染：

- 支持原生图片就发媒体；失败则回退为文本链接或纯文本；
- 不支持表格就转短列表；
- 字段取舍由统一优先级决定，不能改变业务结论；
- 发送多条消息时使用同一 response id，记录部分成功。

## 6. Locale 规范

- Locale 由本轮语言、账号设置和通道设置共同确定；本轮明确语言优先。
- 不把所有非中文语言都默认为英文；语言不确定时可沿用上一轮。
- 菜名、标签和错误文案使用同一 locale；没有可信翻译时保留真实原名并简短解释。
- Emoji、Markdown 只由通道渲染层决定，不写进业务规则。
- 中英文都必须保持同样的真实性、设备确认和错误边界。

## 7. 等待提示规范

只有预计超过约 1 秒的操作才发送短提示。提示的职责是降低等待焦虑，不应提前承诺搜索结果，也不应每次复用同一句。

- 搜索：说明正在按当前关键条件找；
- 图片：说明正在识别，再用真实结果搜索；
- 设备：说明正在检查设备状态，不能说正在启动；
- 不支持编辑/撤回的通道，避免发送过多过程消息。

同一通道应有小型、可测试的变体池；变体必须保持事实等价。

## 8. 通道验收矩阵

每次发布至少覆盖：

1. 中英文菜谱搜索；
2. “这三道哪道最省事”的候选追问；
3. 换一批、上一批与新增忌口；
4. 图片识别成功、低置信度和媒体上传失败；
5. 设备状态、确认、取消、启动未确认、停止；
6. 搜索/记忆/通道依赖失败；
7. 私聊与群聊的用户隔离；
8. Web 两个并发匿名 session 不串线；
9. webhook 未授权和重放请求被拒绝；
10. 同一业务结果在四通道结论一致。

## 9. 目标原则

“同一业务规则，不同表现能力”：搜索、意图、记忆和设备安全必须一致；图片尺寸、Markdown、消息拆分等表现细节可以不同。
